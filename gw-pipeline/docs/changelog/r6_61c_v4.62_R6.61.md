## 背景

CSP `'wasm-unsafe-eval' blob: https://aladin.cds.unistra.fr` 中的
`wasm-unsafe-eval` 是 Aladin Lite WASM 模块的硬需求。
R6.6 / R6.16 / R6.27f 多次调整 CSP，每次都担心"万一哪天不小心删掉，
Aladin 在生产环境默默挂掉，dev 也察觉不到"。

R6.61.c 的解决方案：**前端监听 + 后端日志**——
任何 CSP violation（不只是 wasm-unsafe-eval）都会在 5s debounce 后
POST 到 `/pipeline/security/csp-violation`，后端写入 daily-rotated JSONL
（`/app/logs/csp-violations.log`，保留 7 天）。

dev 在 zjlab 上 `docker logs gw-pipeline | grep csp` 即可立即发现
任何 CSP 回归（不依赖打开浏览器 DevTools）。

## 前端实现 `src/util/cspMonitor.ts`

### 核心监听
```ts
document.addEventListener('securitypolicyviolation', onViolation, { capture: true })
```

### 限流策略
| 机制 | 值 | 理由 |
|------|----|----|
| Debounce | 5s | 页面初次加载常有 burst（Aladin WASM 启动、其他 script） |
| Max batch | 50 | 单条 bad script 可触发上千次 violation；50 是合理上限 |
| Dedup ring | 200 | (effectiveDirective + host + sample[:40]) 去重，ring cap 防内存增长 |
| keepalive | true | 页面 unload 时 fetch 仍能完成 |

### 测试覆盖（10/10）
```
✓ initCspMonitor installs once (idempotent)
✓ captures violations dispatched on document
✓ dedups violations with same effectiveDirective + host + sample
✓ different blockedURI hosts create separate entries
✓ inline/eval violations are kept separately from URL violations
✓ caps batch size at 50
✓ POSTs to /pipeline/security/csp-violation with correct body shape
✓ uses keepalive so fetch survives page unload
✓ swallows fetch errors (does not throw to caller)
✓ dedup ring caps at 200 (does not grow unbounded)
```

happy-dom 不支持 `SecurityPolicyViolationEvent`，测试用 plain Event
+ 手动附加字段 + `as any` 绕过 type check（生产环境真实浏览器正常）。

### 接入 `main.tsx`
```ts
import { initCspMonitor }
initCspMonitor()  // 在 createRoot 之前
```

## 后端实现 `src/pipeline/routes/security.py`

### Endpoint
```python
@router.post("/security/csp-violation")
async def receive_csp_violation(report: CspReport, request: Request) -> dict:
```

### 日志格式（JSONL，一行一条）
```json
{"ts": 1704470400000, "ua": "Mozilla/5.0 ...", "url": "/index",
 "blockedURI": "https://evil.example.com/x.js",
 "effectiveDirective": "script-src",
 "violatedDirective": "script-src",
 "disposition": "enforce",
 "sourceFile": "...", "lineNumber": 1, "columnNumber": 1,
 "sample": "alert(1)", "originalPolicy": "default-src 'self'",
 "client": "10.0.0.42"}
```

### Logger 配置
- 专用 logger `gw.csp.violations`（不污染 root logger）
- `TimedRotatingFileHandler(when='midnight', backupCount=7)`
- 路径 `/app/logs/csp-violations.log`（`CSP_LOG_DIR` env 可覆盖，方便测试）
- 格式 `%(message)s`（因为每条都是 JSON，无需 timestamp 前缀）
- `propagate=False` 避免重复

### 注册（在 `server.py` 中）
```python
try:
    from pipeline.routes.security import router as security_router
    app.include_router(security_router, prefix="/pipeline", tags=["security"])
except Exception as e:
    import logging as _logging_sec
    _logging_sec.getLogger("pipeline.startup").warning(f"security router not loaded: {e}")
```

## 实际使用

### 触发（前端）
任意 CSP-blocked resource 都会自动上报，包括：
- `wasm-unsafe-eval` 被错误删除 → Aladin WASM 模块被 block
- Aladin 加载外部 script 但 `script-src` 没列白
- HiPS tile 被 `img-src` 错误限制
- 任何 XSS 试探（content script 被 block）
- 任何 supply-chain 攻击（第三方 CDN 变更）

### 监控（dev / ops）
```bash
# 在 zjlab 服务器上实时查看
ssh zjlab
docker exec gw-pipeline tail -f /app/logs/csp-violations.log

# 按 directive 统计
docker exec gw-pipeline cat /app/logs/csp-violations.log | \
  python -c "import json,sys,collections; print(collections.Counter([json.loads(l)['effectiveDirective'] for l in sys.stdin]))"

# 找 wasm-unsafe-eval 回归（Aladin 死亡征兆）
docker exec gw-pipeline grep wasm-unsafe-eval /app/logs/csp-violations.log
```

### 为什么只 log 不 alert
- CSP violation 在 dev 模式很常见（inline script 等）。
- Alert 会淹没真信号。
- log + 人工 review 已足够捕获回归。
- 未来如果 violation rate 异常高，可加 Sentry/Rate-limit（留待 R6.62+）。
