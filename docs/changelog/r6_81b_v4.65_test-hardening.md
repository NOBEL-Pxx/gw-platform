# R6.81b — gw-backend deploy pipeline Tier 1 follow-up

## Why

R6.81a (commit `4b59ed1`) shipped the `build-and-deploy-jar.py` wrapper with 19 unit tests. Two important fixes — **H1** (triple-SHA verification local → host → container) and **C1** (`_instantiate_zkb` Windows fallback) — had no dedicated regression tests. This created the risk that future refactors could silently regress the H1 invariant ("abort `docker restart` if any SHA doesn't match") or break the C1 fallback on Windows dev boxes.

Tier 1 #3 adds an explicit `[WARN]` log to `_instantiate_zkb` when `ZKB_SYNC_SCRIPT_FALLBACK` is missing. Without the warning, a missing fallback would surface later as an opaque `RuntimeError` from `zkb.parse_creds()` with no breadcrumb back to the missing file.

## What changed

No production behavior change for users on the happy path. Only failure-mode diagnostics.

## Iron rules added

- **R6.81b-A** — Every deploy-review HIGH (H1) and CRITICAL (C1) fix must have a dedicated regression test before the next R iteration.

## Lessons

1. **A deploy-review fix without a regression test is one refactor away from breaking.** H1's "abort before `docker restart`" invariant is critical enough that a future cleanup of `cmd_deploy` could quietly drop the SHA check. The new `TestTripleShaVerification` class hardens this.
2. **Silent fall-throughs on rare config branches are bugs-in-waiting.** C1's "fallback missing → `Zkb()` with env vars only" branch is exactly the kind of code path that gets tested once on the dev box that has env vars set, and then explodes in prod. The new `[WARN]` log + strengthened test ensures this path surfaces clearly when taken.
3. **Tier 1 #2 came in under budget.** Estimated 30 min, actual ~25 min. Test infra (mock.patch.object on module-level + MagicMock side_effect for `z.run`) was straightforward to extend.
