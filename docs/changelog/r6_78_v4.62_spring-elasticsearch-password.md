# R6.78 — spring.elasticsearch.passwd → password (unblock SPRING_ELASTICSEARCH_PASSWORD env var)

**Date**: 2026-09-10
**Version**: v4.61 → v4.62 (no API change; Spring property + env var naming)
**Status**: SHIPPED + DEPLOYED + VERIFIED

## Summary

Codebase previously used non-standard `spring.elasticsearch.passwd`, so the
`SPRING_ELASTICSEARCH_PASSWORD` env var (added to .env.example in R6.77) was
silently ignored by Spring Boot's relaxed binding. R6.78 renames the Spring
property to the standard `spring.elasticsearch.password`, unblocking the env var.

After this fix, `SPRING_ELASTICSEARCH_PASSWORD` is **LIVE** (not dead weight).

## Why this matters

`SPRING_ELASTICSEARCH_PASSWORD` was the **env var the codebase should have used
all along** (it's the standard Spring Boot relaxed-binding form). The non-standard
`passwd` form was silently broken:

1. R6.98 ES credential fix used `SPRING_ELASTICSEARCH_PASSWD` (matching the typo).
2. R6.77 .env.example refresh added `SPRING_ELASTICSEARCH_PASSWORD` (standard form).
3. R6.77 self-review flagged the dead-weight issue (env var ignored).
4. **R6.78** = the actual fix (rename to standard).

Without this fix, R6.77's `SPRING_ELASTICSEARCH_PASSWORD` env var would be silently
ignored, and the production credentials would only work via the abbreviated
`SPRING_ELASTICSEARCH_PASSWD` — exactly the kind of "magic working" anti-pattern that
makes on-call debugging painful.

## Lessons (R6.78)

1. **gitignore trailing-slash patterns are NOT sufficient for ignoring dir contents**.
   `docker-images/` ignores the dir entry, but `docker-images/**` is required to
   ignore the files inside. The discovery came from `git check-ignore -v` showing
   a match but `git ls-files --others --exclude-standard` still listing the .tar files.
2. **Standard > Custom** for env var naming. Spring Boot relaxed binding supports both
   `password` (standard) and `passwd` (typo), but standard makes env vars predictable
   and tool-friendly. The `passwd` form was a silent trap.
3. **mirror-shared-patterns** caught all 5 sites in one pass; missing any one would
   re-introduce the dead-weight condition.
4. **The fix must come from BOTH directions** (env var rename + Spring property rename).
   Renaming only the env var would have left the property typo and broken SCRAM-SHA-256.
   Renaming only the property would have left the env var still dead-weight.
5. **R6.77's dead-weight finding was a feature, not a bug** — the .env.example refresh
   surfaced the typo, which made R6.78 fixable. Without R6.77's honest review, the
   standard env var would have stayed broken indefinitely.
