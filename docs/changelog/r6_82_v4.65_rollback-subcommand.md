# R6.82 — `rollback` subcommand + pre-deploy backup step

## Why

After R6.81a + R6.81b shipped the unified `build-and-deploy-jar.py` wrapper, the deploy pipeline has triple-SHA verification (H1) + jar-content checks + 120s wait-for-UP timeout. But there was **no way to recover** from a bad deploy without manual SFTP + docker cp + restart from the zjlab shell.

R6.82 closes this gap:
- `cmd_deploy` now rotates `app.jar` → `app.jar.previous` (and `app.jar.previous` → `app.jar.backup` if it already exists) BEFORE docker cp of the new jar.
- New `cmd_rollback` restores the `.previous` jar into the running container, verifies SHA before restart (H1 invariant extended), and waits for `/api/health` = UP.

Without R6.82, a bad deploy (e.g., wrong SHA due to partial docker cp, missing HealthController class) would be unrecoverable without manual intervention.

The backup step runs BEFORE SFTP upload of the new jar, so even if the new jar is malformed, the previous version is preserved for rollback.

## CLI

```
python build-and-deploy-jar.py rollback [--conf] [--timeout SECS]
```

- `--conf`: skip interactive "Type 'yes' to restart" prompt (requires explicit USER authorization)
- `--timeout`: wait-for-UP timeout (default 120s, same as deploy)

## Backup state machine

| Before deploy | After deploy |
|---|---|
| (no app.jar) | app.jar = new, .previous = (none), .backup = (none) |
| app.jar = current, .previous = P1, .backup = B1 | app.jar = new, .previous = current, .backup = P1 |
| app.jar = current, .previous = (none) | app.jar = new, .previous = current, .backup = (none) |

Rotation: `.previous` → `.backup` happens ONLY when `.previous` already exists. This gives 2-deep history (`app.jar.previous` is the immediate rollback target; `app.jar.backup` is the previous-previous if needed).

## Iron rules added

- **R6.82-A** — `cmd_deploy` MUST rotate `app.jar` → `app.jar.previous` (with prior-rotation to `.backup`) BEFORE docker cp of new jar. Hard-coded, no opt-out. Test guard: `TestDeployBackup` (3 tests).
- **R6.82-B** — `cmd_rollback` MUST require explicit `--conf` OR interactive "yes" prompt (per [[r678-classifier-boundary]]). Test guard: `TestCmdRollbackHappyPath` (uses `--conf=True`) + `TestCmdRollbackNoPrevious` / `TestCmdRollbackShaMismatch` (assert no `input()` fires).
- **R6.82-C** — `cmd_rollback` MUST verify SHA inside container of restored `app.jar` BEFORE `docker restart`. Same H1 invariant as deploy, extended. Test guard: `TestCmdRollbackShaMismatch` + `TestCmdRollbackHappyPath` (sequence assertion: SHA-capture < cp < SHA-verify < restart).

## Additional hardening (post-review, R6.82-A1/C1)

- **Post-rotation size check** — after rotation cp returns 0, run `docker exec ... test -s .backup` to confirm the file is non-empty. Defends against partial cp that returns 0 but truncates the file. Aborts deploy if .backup is empty. Test guard: `TestDeployBackupReviewFixes::test_size_check_aborts_deploy_when_rotation_truncated`.
- **Audit print on `--conf`** — `cmd_rollback` emits `[AUDIT] rollback invoked with --conf` so post-mortems can distinguish prompted vs. unprompted rollbacks. Test guard: `TestCmdRollbackReviewFixes::test_rollback_conf_true_emits_audit_print`.
- **Timestamped audit prefix** — every `cmd_rollback` print is prefixed with `=== R6.82 rollback @ <ISO8601>: ...`. Final summary line `=== AUDIT: rollback complete @ <ts>, restart=Xs, health=UP ===` provides structured post-mortem record.
- **`.backup` recovery hint on backup failure** — when backup cp fails, surface the `.backup` jar as a manual fallback path so the operator doesn't have to remember it exists.

## Lessons

1. **Backup is the pre-condition for rollback.** A rollback feature without an automatic backup step is half-built — operator would have to remember to manually backup before each deploy. Worse, a manual backup ritual is the kind of thing that gets skipped under pressure (R6.80-class regression: SHA mismatch aborts post-cp restart → no way back without manual SFTP).
2. **2-deep jar history is YAGNI.** Each extra tier costs an extra docker cp + an extra failure mode in the rotation step. 2-deep (`app.jar` current + `app.jar.previous` one-step undo + `app.jar.backup` safety net) covers the realistic case: an operator notices a bad deploy within one cycle. Three-deep would only matter if bad deploys went undetected for multiple cycles, which the `/api/health = UP` check makes unlikely.
3. **SHA verification extends naturally.** R6.82-C reuses the H1 invariant ("verify SHA before restart") pattern from R6.81a. The test `TestCmdRollbackShaMismatch` is structurally identical to `test_container_sha_mismatch_aborts_before_restart` — same shape, same defense. Review-fix C3 extended this to assert call sequence (SHA-capture < cp < SHA-verify < restart), not just whether SHA-verify fires.
4. **Subparser help text lives in parent's --help.** A subtle argparse quirk caught by `test_rollback_help_describes_restart` initial failure: `python rollback --help` shows only optional arguments, NOT the subparser's help text. The help text "R6.82: restore previous container jar + restart" appears only in `python --help`.
5. **Review-fix tests need to mock reality, not just structure.** When adding `test -s` size-check to backup-step code, the existing `TestDeployBackup._make_mock_z` mock needed updating too. Mocks that hardcode "('', 0)" for every unknown command are brittle — the cmd they mock can grow new commands. Mitigation: catch-all default-OK returns for safe commands, explicit overrides for fail scenarios.
