# R6.83 — Parallel `/api/health` component probes

## Why

R6.80 added `/api/health` with sequential probes: ES first (~5-10ms), then Mongo (~5-10ms), then aggregate. Sequential wall-clock = sum = ~15-20ms. R6.80 L4 daily-log lesson noted "Health probes are sequential — R6.81 candidate for parallelization".

R6.83 closes the latency gap:
- **ES + Mongo now run concurrently** via `CompletableFuture.supplyAsync(...)` on a fixed 2-thread executor.
- **Wall-clock = max(ES, Mongo)** instead of sum. Expected ~5-10ms instead of ~15-20ms (~50% reduction).
- **Per-probe timeout** via `.orTimeout(...)` prevents pool starvation if a probe hangs (driver bug, GC pause, DNS stall).
- **Custom 2-thread daemon executor** (not `ForkJoinPool.commonPool()`) provides bounded thread count + explicit lifecycle.

R6.83 also closes a **silent-failure risk** flagged by the R6.83 3-perspective deploy review (D1): the R6.81a jar-content verifier's `KEY_CLASSES` whitelist cannot distinguish R6.83 bytecode from R6.80 bytecode (same class path, same API surface, only bytecode body changed). Without deploy-time verification, a `mvn -pl start package` (forgetting `-am`) would silently ship stale sequential-code jar and pass `/api/health` UP. R6.83 ships a marker log line + post-deploy marker check that catches this.

## Implementation

### HealthController.java

```java
// @PostConstruct — initialize 2-thread daemon executor with named threads
@PostConstruct
public void initProbeExecutor() {
    AtomicInteger seq = new AtomicInteger(0);
    this.probeExecutor = Executors.newFixedThreadPool(2, r -> {
        Thread t = new Thread(r, "health-probe-" + seq.incrementAndGet());
        t.setDaemon(true);
        return t;
    });
    log.info("R6.83: HealthController probe executor initialized (2 threads, daemon=true)"); // MARKER
}

// @GetMapping("/api/health")
public Response<Map<String, Object>> health() {
    if (probeExecutor == null) { /* null-guard 503 */ }

    CompletableFuture<Map<String, Object>> esFuture = CompletableFuture
        .supplyAsync(() -> checkComponent("elasticsearch", this::probeElasticsearch), probeExecutor)
        .orTimeout(11, TimeUnit.SECONDS)
        .exceptionally(ex -> componentStatus("elasticsearch", false, 11000L));

    CompletableFuture<Map<String, Object>> mongoFuture = CompletableFuture
        .supplyAsync(() -> checkComponent("mongo", this::probeMongo), probeExecutor)
        .orTimeout(12, TimeUnit.SECONDS)
        .exceptionally(ex -> componentStatus("mongo", false, 12000L));

    CompletableFuture.allOf(esFuture, mongoFuture).join();
    // ...aggregate and return
}

// @PreDestroy — graceful shutdown with 11s awaitTermination, fallback to shutdownNow
@PreDestroy
public void shutdownProbeExecutor() {
    if (probeExecutor != null) {
        probeExecutor.shutdown();
        try {
            if (!probeExecutor.awaitTermination(11, TimeUnit.SECONDS)) {
                probeExecutor.shutdownNow();
            }
        } catch (InterruptedException ie) { Thread.currentThread().interrupt(); probeExecutor.shutdownNow(); }
    }
}
```

## Iron rules added

- **R6.83-A** — `probeExecutor` MUST be initialized in `@PostConstruct` and shutdown in `@PreDestroy` with `awaitTermination(11s)`. Prevents JVM hang on shutdown. Test guard: structural (PostConstruct + PreDestroy methods exist).
- **R6.83-B** — Probes MUST use `CompletableFuture.allOf` + `.orTimeout(...)` not sequential awaits. Prevents pool starvation on hang. Test guard: `parallelProbesRunConcurrently` proves concurrency; timeout is structural.
- **R6.83-C** — `probeExecutor` MUST use daemon threads with named prefix `health-probe-N`. Prevents JVM block on shutdown + improves thread-dump forensics. Test guard: structural (ThreadFactory sets daemon=true).
- **R6.83-D** — `HealthController.health()` MUST return 503 if `probeExecutor == null`. Prevents NPE-500-storm after failed startup. Test guard: structural (null check at top).

## Lessons

**L1**: `KEY_CLASSES` whitelist (R6.81a) cannot catch refactor-only changes (same class path, same API). Need runtime marker for "did the new bytecode actually deploy" verification.

**L2**: `CompletableFuture.allOf().join()` is preferred over `thenCombine` because `thenCombine` has subtle ordering issues when one branch throws. `allOf + individual .join()` is more defensive.

**L3**: `Executors.newFixedThreadPool` with `LinkedBlockingQueue` is unbounded by default — fine for 2 threads + bounded load (health endpoint), but if probe latency spikes, queue can grow. Document polling budget externally.

**L4**: Reflection-based tests (no Spring context) are 10x faster but lose integration coverage. zsmoke `api-health` check (R6.80 #4) covers the integration gap.

**L5**: `awaitTermination` in `@PreDestroy` is the R6.79 defensive coding pattern applied to executor lifecycle: graceful drain first, force shutdown as fallback.

**L6**: Per-component `orTimeout` ceilings (11s ES, 12s Mongo) are R6.80 socket/connect timeouts (5s/10s) + 1-2s headroom. Future R6.84+ zsmoke `api-health-parallel` check could assert `max(latency_ms) < sum(latency_ms)` for prod concurrency proof.
