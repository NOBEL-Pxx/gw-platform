# R6.79 — JWT_SECRET defensive check + MongoDB password env var rename

**Date**: 2026-09-10 (deploy 2026-09-11)
**Version**: v4.62 → v4.63 (security hardening; no API change)
**Status**: SHIPPED + DEPLOYED + VERIFIED

## Summary

R6.79 closes **two production security gaps** that R6.78 + 3-perspective review uncovered:

1. **JWT secret was silently defaulting to a publicly-known literal.** The
   `application.properties` line `jwt.secret=${JWT_SECRET:gw-platform-jwt-secret-key-2026-v4.7}`
   used a `:default` fallback — if `JWT_SECRET` env var was unset, the app
   happily started and signed every JWT with that publicly-known key. **Any
   prior deployment that didn't override JWT_SECRET was COMPROMISED.**
   `JwtUtil.java` had the same `:default` bug.

2. **MongoDB password property placeholder was dead weight.** The
   `application*.properties` line `spring.data.mongodb.password=${MONGO_PASSWORD}`
   referenced a non-existent env var. The actual `MONGO_APP_PASSWORD` in `.env`
   reached the app via Spring Boot relaxed binding (`SPRING_DATA_MONGODB_PASSWORD`).
   The placeholder was misleading — R6.79 makes it direct.

R6.79 enforces **fail-fast at startup** for both: `${VAR:?error message}` syntax
makes Spring Boot (or docker-compose) refuse to start if the env var is unset.

## Why this matters

**Without R6.79**: any deploy that forgot to set `JWT_SECRET` would silently
run with a publicly-known signing key. An attacker reading the source code
(or the .env.example comment) could forge tokens for any user, bypassing
authentication entirely. The defensive check now makes this a deploy-time
error instead of a silent compromise.

**Without R6.79**: the MongoDB password placeholder was unreachable code. If
the relaxed binding contract ever changed (e.g., Spring Boot removed the
legacy mapping), MongoDB auth would silently fail with a confusing error.
R6.79 makes the dependency explicit and adds `:?` for fail-fast parity with
the JWT_SECRET defensive check.

## Discovery (from 3-perspective review)

R6.79 was triggered by the **deploy reviewer's systematic investigation**:

1. Read the property files — found `${MONGO_PASSWORD}` placeholder.
2. Grep `.env` for `MONGO_PASSWORD` — **0 matches** (only `MONGO_APP_PASSWORD` exists).
3. Concluded: relaxed binding was carrying the value, but the placeholder was dead.
4. Same review caught `${JWT_SECRET:default}` — the **CRITICAL** finding.

The security reviewer then ran adversarial verification and confirmed:
- `${MONGO_APP_PASSWORD}` placeholder is live (binds via env var forwarding)
- `${JWT_SECRET:default}` was actually shipping the publicly-known default
- `JwtUtil.java` had the same `:default` bug — both layers were compromised

## Lessons

1. **`:default` on sensitive values is a security anti-pattern.** Spring Boot's
   `${VAR:default}` syntax is convenient for non-secret config but dangerous
   for secrets — the default ships in source code and is effectively public.
   Always use `:?` for required secrets.

2. **Dead placeholders are tech debt with security implications.**
   `${MONGO_PASSWORD}` didn't break anything (relaxed binding carried the value),
   but it masked the real env var contract. Reviewers must read `application*.properties`
   AND `.env` AND `docker-compose.yml` together to find mismatches.

3. **3-perspective review caught what one perspective missed.** Security
   review alone found the JWT `:default` bug but didn't catch the env var
   mismatch (deploy reviewer caught that). Deploy review alone would have
   flagged `.env` missing JWT_SECRET but missed the Java code `:default`.
   Parallel perspectives = comprehensive coverage.
